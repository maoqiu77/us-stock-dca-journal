## 1. 最重要的结论

**项目值得继续打磨，但下一阶段优先级应是“数字可信、链路连通、复盘可用”，而不是增加更多指标、更多模型或更多页面。**

建议把产品定位收敛为：

> 一个记得我的持仓、计划和历史判断，能解释数据从何而来，并帮助我检查自己是否遵守计划的个人投资助手。

核心闭环应为：

```text
可信持仓与原始记录
    → 发现值得关注的变化
    → 使用经过确认的上下文进行 AI 分析
    → 用户记录自己的决定
    → 关联实际交易或保持不动
    → 按条件或日期回访
    → 基于当时可知信息复盘
```

### 1.1 先做这五件事

| 顺序 | 改进 | 为什么值得优先做 |
|---|---|---|
| 1 | 修正盈亏口径、行情缺失和截图回填边界 | 错误或伪完整的数字会破坏所有后续分析 |
| 2 | 让日历中的每类记录可打开、可新增、可正确归档 | 日历必须是工作入口，而不只是展示“哪天生成过 AI” |
| 3 | 把 AI 回答、个人想法、决定、实际交易和复盘连接起来 | 形成区别于普通聊天工具的长期个人价值 |
| 4 | 总览减少首屏负担，看板保持上下文和数据状态 | 用户无需来回切换页面猜测“现在到底怎样” |
| 5 | 补生产成本保护、发布门禁和面向新人的说明 | 作者自己能使用，不等于陌生用户能够可靠使用 |

### 1.2 已有优势：应该利用，不应重复建设

| 已有基础 | 本次看到的证据 | 正确的下一步 |
|---|---|---|
| 小程序区分持仓校准与真实流水 | 有 checkpoint、修订和冲突处理路径 | 修复截图指标适用性；向桌面移植语义，而不是重新设计一套 |
| 小程序已经有日历和个人手记 | 七列日历、选择日期、记录与会话入口 | 增加类型、关联关系和回访，不再做一个并行日历 |
| 小程序已做发送前预览和授权 | 预览、确认及云端能力检查 | 优化说明和默认范围，降低操作负担但不绕过确认 |
| 小程序 AI 结果已有结构化展示 | 证据、反方观点、观察条件、缺失信息和来源 | 强化“每条判断 → 原始证据 → 后续决定”的跳转 |
| 本地工作区已有可靠性机制 | 分区、校验、修订、恢复点和 outbox | 做中断与恢复测试，不另建一套消息队列 |
| 桌面 AI 已有研究快照和记忆检索 | 快照有效期、幂等确认、BM25 原文检索及来源限制 | 评估检索质量、补用户可见的范围控制 |

以上是已观察到的实现基础，不代表所有异常路径均已验证。[S25][S28][S29][S31][S32][S18][S19][S20][S21]

## 2. 用四条真实任务链衡量产品

### 2.1 第一次使用：没有 AI 配置也能成功

**目标任务：** 新用户建立一个可信持仓，知道哪些是实时或参考行情、哪些只是导入时的历史信息。

建议入口只给三种选择：“记录当前持仓”“录入真实交易”“先了解产品”。演示必须进入明确隔离的演示工作区，不能向真实账本或生产行情回填样例。

第一笔数据完成后立即展示差异：新增了什么、成本是否已知、还有什么待确认。AI 配置应是后续能力，不是使用本地记录的前置条件。

### 2.2 每日查看：知道状态，也知道哪些信息不知道

**目标任务：** 用户打开总览，能找到持仓状态、数据缺口、计划偏离和最近记录；无需读一篇 AI 长文才能理解账户。

首屏问题应当是“哪些数字可靠”“有什么值得我查看”，而不是“今天系统建议买什么”。没有异常时应明确表示无新增待处理事项，不能为了活跃度制造交易冲动。

### 2.3 发起研究：不用重新解释自己

**目标任务：** 从某个持仓进入 AI，自动带上标的身份、选定持仓、已确认计划和相关原始记录；用户能调整范围。

研究结束后应能写下自己的想法、选择暂不行动或安排回访。不要把模型建议自动转换成用户决定，更不能转换成成交记录。

### 2.4 周末复盘：不只问“涨没涨”

**目标任务：** 用户回到某次分析，看到当时依据、自己的决定、之后发生的事实，以及是否遵守事先规则。

复盘更应检验过程质量，而不是通过事后价格证明当时的判断“必然正确”。缺少成交、价格或时间信息时，明确不能得出完整收益结论。

### 3.1 尚不能宣判为缺陷，但必须验证的事项

**R01：时序一致性。** 小程序估值路径既有带截止时间的投影，也有公共行情、基金净值等后备读取。需要验证历史回看是否可能引入当时尚不可知的数据；目前没有运行证据，不能宣称已经发生“未来数据泄漏”。[S25]

**R02：用户主动清空自选后的升级。** 看板有首次基金种子初始化逻辑，需要区分“从未初始化”和“用户已经清空”，避免升级时重新加回用户不需要的自选。[S33]

**R03：系统文本被当成用户原创。** 工作区欢迎语的分类使用了个人原创类别。应验证这种系统生成内容是否可进入个人原文检索；建议独立标记为系统说明，并默认排除，不把欢迎语作为用户投资偏好。[S32]

**R04：跨环境发布。** 真实云端的授权隔离、清理任务回执、模型费用、市场数据使用权限、微信平台配置和真机表现，需要部署凭证与执行记录。发布准备文档列出了相关待办，但本次未独立验证完成状态。[S03]

**R05：历史源码与运行产物是否一致。** 构建脚本已有发布清单能力；需要将实际安装包、云函数代码及当前 SHA 对齐，不应只依据根包版本号猜测运行版本。[S35]

## 4. 优先修复：数字与记录必须可信

### 4.1 F01：区分“涨跌幅”“当前持仓价格变动估计”“真实当日盈亏”

以下为**独立合成算例**，不是用户真实资产，也不是项目测试运行结果。

假设当前持有 10 股，昨收 100，现价 110，没有日内成交：

| 计算 | 结果 |
|---|---:|
| 当前市值 | 1,100 |
| 相对昨收涨幅 | 10% |
| 当前代码公式得到的金额：当前市值 × 10% | 110 |
| 当前数量对应的价格变动：10 × (110 − 100) | 100 |

反向例子：现价 90 时，当前公式得到 −90，价格变动应为 −100。平盘时均为 0。审查者以 Decimal 对这三个算例进行了独立校验。

对于**同一报价基准、同一复权口径、数量固定**的情形：

```text
优先：price_change_proxy = current_quantity × (price − previous_close)

仅在契约保证一致、r > -1 且基准明确时：
price_change_proxy = current_market_value × r / (1 + r)
其中 r = change_percent / 100
```

这只是“按当前数量估计的价格变动”，**不自动等于真实当日账户盈亏**。存在日内买卖、分红、费用、拆股、转入转出时，必须依赖完整事件和价格基准另算。

**修复要求：** 优先使用同一报价对象中的价格和昨收；缺失日期、基准不兼容或无法处理公司行动时返回未知并解释。不能在 UI 内仅替换一个乘除式，就继续把结果无条件称为“今日盈亏”。

**验收：** 上涨、下跌、平盘、缺昨收、日内新增仓位、不同交易时段、拆股、负或非法基准都应有测试。基金净值涨跌额应标注对应净值日，不借用股票“盘中今日”标签。

### 4.2 F02：截图是历史观察，不能随持仓数量变化而继续代表当前金额

静态路径显示：部分截图收益校验与展示合计并未共用同一个有效性条件。[S25][S26]

建议以此合成场景复现：

```text
T0：导入截图，10 股，截图市值 1,000
T1：真实卖出 5 股，当前数量变成 5 股
T2：没有可用行情
预期：当前市值未知；历史截图仍显示“当时 10 股 / 1,000”
禁止：把 1,000 作为现在 5 股的市值，或纳入当前合计
```

引入统一的“历史截图是否适用于当前展示”判定，供行、合计、收益率和导出共同调用。条件至少包括资产身份、币种、数量、基线修订、成本口径及冲突状态。比较数量须使用规范化 Decimal，不能只比较字符串。

同样数量不一定代表同一仓位状态：先卖后买、成本变更或基线修订也可能让旧截图失效。应优先依赖账本/基线版本，再使用数值匹配。

**推荐展示：** 当前估值和历史截图分成两个区域。即使历史截图仍可作参考，也不能使“当前行情覆盖完整率”提高。不要按剩余数量机械缩放截图中的持仓盈亏。

### 4.3 F03：缺行情时，“未知”比好看的数字重要

桌面总览应停止把成本价当作市场报价。建议定义三种互不混淆的概念：

| 概念 | 可以使用什么数据 | 不允许冒充什么 |
|---|---|---|
| 当前或最近可用估值 | 合格报价、明确时间与口径 | 未披露时间的实时值 |
| 已知部分合计 | 有效行的金额及覆盖范围 | 完整账户总额 |
| 历史观察 | 截图、旧净值、旧收盘价 | 当前仓位的实时估值 |

“总资产盈亏”应在缺少现金与完整资产口径时改为“持仓浮动盈亏”。桌面日变动合计还应按**实际持仓的有效报价覆盖率**判断完整性，不能因为自选列表里有一个有效报价就让缺失持仓显示为零。[S10][S11]

**空仓不等于数据缺失：** 已确认空仓的持仓市值可为 0；有持仓却无报价的市值是未知。现金未完整记录时不能用“预设总资产 − 持仓成本”冒充真实现金余额。历史桌面存在这样的推导入口，迁移时需显式区分估算和已对账余额。[S12]

### 4.4 F04：持仓校准不能伪装成真实成交

已追踪到桌面截图页面实际调用覆盖函数，因此不只是未使用的辅助代码。当前覆盖通过合成买卖调整账面持仓，适合维持数量，却不适合被解释为用户的真实投资行为。[S12][S13][S14]

建议桌面借鉴小程序已经采用的边界，增加或适配：

```text
真实成交：用户确认过的成交事实
期初余额：从某个时间开始接管记录
持仓校准：对某一时点余额的确认
历史截图：带来源和观察时间的辅助证据
```

完整截图与局部截图也必须分开：局部截图只能更新选择的标的；完整覆盖前展示“新增、变化、将不再计入”的差异，由用户逐项确认。不能因为识别遗漏或某张图片失败，就默认其他持仓已经清空。

**迁移不能粗暴删历史。** 先备份和预览，再识别旧导入事件。不要只凭中文备注自动删除交易，因为用户可能修改备注或存在同名真实记录。无法可靠判断的旧事件保留为“待确认的历史导入”，并从需要真实成交的行为分析中隔离。

**验收：** 导入当前持仓不增加真实成交笔数；连续重复导入不新增成交；真实交易不会被覆盖清空；退出或失败可恢复旧版本。

### 4.5 F05：视觉能力公开前，补齐独立费用保护

当前云入口默认不会自动开启视觉能力，但开启后其配额配置与文本 AI 不同；并发为 1 只能限制同时处理数量，不能限制一天连续调用的总成本。发布准备资料也把这件事列为后续生产准备项。[S36][S03]

建议生产模式必须满足“用户额度、全局预算、请求幂等、原子预占、熔断开关”五项。已调用供应商但结果不明的请求，不应因客户端取消就释放预算并允许再次计费。

**尊重测试模式原有选择：** 可以保留明确隔离的不限额测试配置；但它不能被当作默认公开生产配置。这里不是要求偷偷恢复或改变开发测试限制，而是要求生产环境显式证明成本边界。

## 5. 总览：从“展示许多数值”改成“告诉我账户现在是什么状态”

### 5.1 首屏信息层级

建议小程序默认首屏如下。**这是拟议布局，不是现有应用截图；其中数字为合成示意。**

```text
持仓                         [币种 CNY ▼] [记录]

已知持仓市值                 82,400
持仓 6 项 · 5 项有有效估值 · 1 项待补数据
最近报价 14:35 · 含延迟行情   [查看来源]

持仓浮动盈亏      按当前数量估计的价格变动
部分已知 +2,400   暂不可完整计算

需要查看
“有 1 项持仓缺少报价”                 [处理]
“你上次设置的复盘日期已到”             [回访]

我的持仓                    [简洁 / 详细] [排序]
标的名称 / 市场 / 币种
市值 · 浮动盈亏
报价状态 / 数据日期                   [展开]

[记录真实交易] [校准持仓] [写手记]
```

首屏不应该同时承载所有技术指标、所有策略信号和全部操作按钮。将细分指标收进标的详情或详细模式。

### 5.2 指标契约：数字旁边需要边界

| 指标 | 呈现规则 | 缺失时的行为 |
|---|---|---|
| 持仓市值 | 同一展示币种的合格估值；标明覆盖数和时间范围 | 显示“已知部分”或“未知”，不回填成本 |
| 持仓成本 | 来自账本或确认的期初成本；说明成本口径 | 成本未知时不展示精确收益率 |
| 持仓浮动盈亏 | 市值减同一仓位口径下的剩余成本 | 缺少任一条件则未知 |
| 当日变动 | 先明确是价格变动估计，还是完整事件重建的日盈亏 | 缺基准时显示原因，不显示 0 |
| 仓位比例 | 写清“占已知估值”“占完整持仓”还是“含现金总资产” | 未完成估值不能伪装成全组合百分比 |
| 现金 | 已记录并对账的现金，或明确标识的用户录入数 | 不用倒推数冒充实账余额 |

小程序当前已区分币种并有部分覆盖提示，应沿此方向完善，而不是撤掉已有状态以换取更漂亮的单一总额。[S25][S27]

跨币种合计不作为第一阶段必做项。以后增加时必须记录汇率对、来源、时间及换算口径；没有可靠汇率就按币种分别展示。多账户合并也应先解决身份、余额和现金流边界，再做一个看起来完整的总资产卡片。

### 5.3 持仓列表：简洁模式优先，详细模式保留

小程序默认每行突出名称、市值和浮盈，再用一行显示来源时间和关键状态。数量、单位成本、价格、仓位比例等放入展开区。保留可选宽表格，服务熟悉表格的用户，而不是让所有人都被迫横滑。

桌面默认展示“实际持仓”，观察列表通过切换查看。固定标的列、记住列配置和排序，新增行或刷新报价时不突然移动正在阅读的行。筛选结果要有明确重置入口，避免用户误以为资产消失。

建议排序提供：用户固定顺序、名称、市值、仓位、需要处理；不要默认仅按短期涨幅排列。用户自己的计划偏离可作为查看线索，但不能把不完整数据包装成精确的投资风险评分。

### 5.4 “需要查看”卡片应是规则驱动，不依赖每次问模型

优先使用可以确定性计算的事项：缺失成本、报价过期、持仓校准冲突、未完成请求、到期回访、用户已确认阈值被触发。

最多显示三项，其余折叠。每项必须有产生原因、数据时间、下一步入口和消除条件。没有确认过目标仓位时，不提示“偏离目标”；模型不能代替用户制定目标。

**禁止的呈现方式：** 用红色大字宣称“风险极高”，却没有给出计算口径；把参考行情当实时突破；以 AI 文字生成“今日必须处理”的买卖任务。

### 5.5 历史曲线：宁可晚做，也不要画出虚构收益

可以先提供真实账本事件数、持仓变化和数据覆盖率。净值、累计收益和回撤曲线必须建立在完整的外部现金流、估值与时间轴之上。

只有当前持仓截图时，可展示“从开始记录以来的观察”，不能补出过去从未记录过的账户净值。图上区分无数据、估算、已对账，遇到缺口不要用连续线暗示完整可知。

## 6. AI 日历：升级成“事实、判断与复盘”的时间轴

### 6.1 日历不应该只是回答列表

建议同一时间轴支持以下类别。实现时复用已有记录及引用，不为每种展示再复制一份正文。

| 类别 | 回答的问题 | 点击后应该去哪里 |
|---|---|---|
| 真实交易 | 我实际做了什么？ | 成交详情及其来源 |
| 持仓校准 | 我确认了什么余额？ | 校准前后差异，不显示成成交 |
| 个人手记 | 我当时怎么想？ | 原文、修订和所属日期 |
| AI 分析 | 模型基于什么判断？ | 对应分析轮次和冻结来源 |
| 我的决定 | 我如何回应这次分析？ | 决定、理由及引用 |
| 回访事项 | 什么条件或日期要重新看？ | 检查状态及完成记录 |
| 外部事件，可选 | 标的发生了什么公开事件？ | 外部来源、事件日期和更新时间 |

外部事件不是第一阶段必做。没有可靠事件源时，先支持用户手工添加，不允许模型根据印象编出财报日或公司行动日期。

### 6.2 两端分别改，避免重复建设

**桌面：** 首先修复 F06–F08。七列、星期标题、月初偏移、今天标记和选中态必须正确；没有记录的日期也可选择。按条目类型分发，而不是统一要求 `session_id`。失败、进行中和结果未知的分析应可打开状态详情，不应该点击无反应。[S15][S17]

**小程序：** 已有七列日历和日期手记，应增加分类计数、日期摘要、标的筛选和关联的回访状态，而不是换一套存储或重新新增“日历功能”。[S28][S29]

两端均应把“已有记录”“今天”“当前选中”“待回访”区分开，不只用颜色。键盘、读屏和大字号状态需要可测试的标签。

### 6.3 推荐页面结构

```text
AI 手记                          [新建]

[今日] [日历] [会话]                 [搜索]

2026 年 10 月                  [上月] [下月]
周一 周二 周三 周四 周五 周六 周日
... 日期网格，标记记录类别和回访数量 ...

10 月 3 日                         [写手记]
个人记录 2 · AI 分析 1 · 待回访 1

个人手记：我暂时不行动的原因
AI 分析：本次与上次有哪些变化
我的决定：继续观察，等待自己设定的条件
回访：检查某个已确认条件是否仍成立

[只看某标的] [按类型筛选] [查看当天完整时间轴]
```

手机端优先当天清单，月历可折叠；桌面可用左侧月历、右侧清单和详情。不要在顶部放一个占据整屏的月历，再把正文和聊天堆成多个独立滚动区域。

### 6.4 日期模型必须清晰

建议区分：

```text
journal_date：用户归档或补记到哪一天
created_at / updated_at：实际写入或修订时间
market_trading_date：行情属于哪个交易日
source_as_of：事实本身的观测时间
source_available_at：系统何时可以知道该事实
```

当前产品有上海业务日期和纽约市场时间的既有约定，应明确沿用，而不是直接按用户设备时区重写历史记录。[S34][S38]

用户身在日本，不意味着美国交易日、上海账本日和设备日期必须合并。展示可以本地化，但归档规则需要稳定。午夜跨日请求应固定一条归档规则并测试，不通过重试改变原分析所属日期。

补写过去手记时，保留“归档到过去某日”和“今天补写”的区别。历史回测或当时知识复盘，不能把今天补写的认知自动当作过去已经知道的事实。

### 6.5 月历查询与缓存

桌面后端应提供轻量月份摘要及分页日清单；具体名称可与现有路由规范对齐：

```text
拟议：monthSummary(month, filters)
返回：每天各类型计数、待回访数量，不返回所有长正文

拟议：dayEntries(date, filters, cursor)
返回：统一排序的条目、稳定 ID、类型、状态、详情引用
```

这不是要求另建一个日历数据库。桌面可以在现有表上增加范围查询、索引与适配视图；小程序可在现有工作区上建立可重建的日期索引。

新增、删除、修订记录后，更新受影响日期和月份的缓存；不能只刷新手记选项列表。排序使用稳定的时间和 ID，不因不同类型分批拼接而跳动。[S16][S17]

### 6.6 更有特色的三个日历功能

**“当时为什么”：** 进入过去某天，默认先展示当时的原始依据、计划和决定；点击后才展示后续结果，减少后见之明。

**“这次与上次有什么不同”：** 比较同一标的或同一组合的两次分析快照，先以确定性逻辑列出持仓、计划、事实及缺失信息的变化，再让 AI 解释这些变化可能意味着什么。不能只让模型泛泛总结聊天记录。

**“待回访收件箱”：** 将用户确认的回访条件汇总到一个轻量清单。状态包括等待、可核查、需补数据、已完成、已取消。应用没有实际后台执行能力时，写明“下次打开时检查”，不要假装实时监控。

## 7. AI 效果：从更长回答，转向更可靠的个人理解

### 7.1 保留现有的证据卡，增加可执行关联

小程序已经展示结构化的证据、反方观点、观察条件、缺失信息和来源信息。因此近期不是“再造结构化输出”，而是让这些块真正连接用户任务。[S31]

每条重要判断应能展开：引用哪条来源、来源何时形成、是否属于用户假设、有哪些限制。算得出的金额和仓位比例由本地或领域层计算，不让模型重新心算并覆盖账本数值。

“观察条件”应有明确主语：是用户自己提出的假设、公开事实待更新，还是模型提出的待核查问题。模型的条件不会自动成为个人投资计划。

### 7.2 先打通“回答 → 我的想法”

当前会话页面已经捕获被选中的回答 ID，但保存想法时仍走独立个人记录路径。这是很适合小步改进的切口，不需要替换聊天架构。[S30][S32]

建议“写下我的想法”保留：

```text
原会话、原消息、原分析轮次
涉及的标的
用户实际写下的正文
用户选择的归档日期
实际创建时间和修订信息
```

原消息被删除后，想法的处理应遵从清晰的删除策略：要么连同派生内容一起删除，要么保留用户正文并显示“原引用已删除”；不保留不可见但还能被检索的旧副本。

### 7.3 再增加“我的决定”，不是把笔记强行变成交易

建议允许用户选择：

| 用户选择 | 系统含义 | 不代表什么 |
|---|---|---|
| 暂不行动 | 用户决定继续观察 | 不是漏处理或失败 |
| 接受部分分析 | 记录同意哪些判断及原因 | 不是已经执行交易 |
| 保留不同意见 | 保存反对理由 | 不是需要 AI 劝服 |
| 设置回访 | 创建用户确认的日期或条件 | 不是自动下单 |
| 关联真实交易 | 指向已经确认的账本事件 | 不根据自然语言自行造一笔成交 |

一个决定可以关联多条分析；一条分析也可以对应多个决定，但实际成交必须引用唯一真实事件，不能重复写入。

### 7.4 上下文应分为四层

| 层次 | 内容 | 使用原则 |
|---|---|---|
| 确定事实 | 已确认持仓、交易、合格行情 | 由程序计算和校验 |
| 用户原文 | 买卖理由、手记、亲自确认的判断 | 可引用，不等于客观事实 |
| 用户计划 | 已确认目标、期限、规则及其生效时间 | 不从模板默认值猜测偏好 |
| AI 历史 | 以前生成的分析和摘要 | 明确标为模型产物，不能递归升级成事实 |

已有自动上下文和原文检索可以继续使用。优先改进相关性、时间过滤、去重、出处和用户排除能力；没有评测证据前，不必迁移到向量数据库或多 Agent 编排。[S19][S20][S21]

**特别要防止“伪记忆”：** 一次提问不等于长期偏好；系统欢迎语不等于用户原创；AI 的建议不等于用户已批准的计划；持仓截图不等于真实交易历史。

### 7.5 用户看得懂的发送范围

桌面同一次点击连续预览与执行的路径，应改为用户可理解的范围确认。可采用首次明确授权、之后范围不变时简化确认的方式，而不是每次都弹冗长提示。[S16]

发送前至少显示：

```text
本轮使用：选定持仓 / 已确认计划 / 相关个人原文 / 会话历史
本轮不使用：未选择的账户 / 已删除记录 / 无法验证的报价
发送到：项目云服务或本地配置的模型服务
本轮范围变化：新增了哪些数据类型或接收方
```

用户可以排除某条原文；排除后不能由自动检索又加回来。切换模型接收方、扩大数据范围或改变授权版本时，重新确认。

小程序已有实际预览和授权流程；主要改进是让摘要更容易理解、错误定位更清楚，而不是降低现有边界。[S29][S30]

### 7.6 默认给用户一个容易回答的任务，而不是一张研究参数表

普通模式先提供“检查持仓变化”“复盘我的计划”“研究一个自选标的”三个任务。标的和相关上下文由入口带入；周期、K 线数量和工具能力放进高级设置。

分析结果第一屏应回答：本次任务有没有足够资料、最关键的变化是什么、哪些还不能判断、下一步是补资料还是写下决定。完整推导留在展开区域，不能用一个模糊的“综合评分”代替依据。

### 7.7 复盘指标不采用“AI 炒股胜率”

建议衡量来源可追溯率、计算一致性、计划遵守情况、回访完成情况和用户对上下文相关性的评价。即使结果赚钱，也可能违反了自己的风险规则；即使短期亏损，也不能仅凭结果断言原决策不合理。

没有标准答案时，用成对人工评审比较两个版本的相关性与谨慎程度。不要让同一个模型既出答案又单独证明自己回答正确。

## 8. 市场看板：少一点信息堆叠，多一点稳定比较

### 8.1 三种视图，而不是无限增加卡片

建议复用现有行情和自选服务，增加保存视图：

| 视图 | 默认关注点 | 与持仓的关系 |
|---|---|---|
| 我的持仓 | 对已持有资产的影响、数据状态 | 基于当前真实持仓 |
| 我的观察 | 观察理由、最近变化、上次研究 | 用户自选，不自动买入 |
| 市场参考 | 宽基或分类参考，不承诺全面覆盖 | 可选，与账本分离 |

现有桌面看板已有分段、自选管理、搜索、排序与修订冲突控制，应继续利用。重点是保存筛选状态和阅读位置，而不是重建这些基础能力。[S22][S23]

“加入观察”和“添加持仓”必须是不同操作。持仓减少或清空时，观察列表是否保留由用户选择，不能随账户变化悄悄改掉。

### 8.2 刷新不应该让内容消失

小程序国内看板当前在获取新数据前清空行。建议改成“保留上一次内容 + 行内更新状态”，新数据返回后稳定替换。[S33]

首次加载可显示骨架；已有内容时不整屏闪烁。失败时保留旧数据并显式标记时间、失败原因及重试，不把旧数据冒充刚更新成功。切换页面后停止无意义轮询，重新进入时按新鲜度决定是否刷新。

排序和过滤结果变化可提示“有更新”，用户主动应用或在非交互时更新，避免手指刚要点某行时行位置突然改变。

### 8.3 不同资产不要共享一个含糊的“价格”

美股成交价、公开参考报价、基金净值、ETF 溢价参考的来源和时间含义不同。现有契约已经包含价格类型、交易日、时效性、来源等字段，应把这些信息投射到界面，而不是在适配器里留着、页面上抹平。[S38][S39][S40]

建议列标题具体到“参考价”“最近收盘”“单位净值（净值日）”。ETF 参考溢价没有同步基准时，应披露计算条件，或直接不展示精确的实时标签。

比较最多先支持两到三个标的，并说明比较区间、币种和数据覆盖。基金可展示适合的净值信息，股票可展示成交行情信息，不用大量“不适用”占据同一宽表。

### 8.4 看板与 AI 的衔接

从看板进入研究时，携带稳定资产 ID、用户当前选定周期及对应数据快照引用；不要只传一个可能重名的 ticker。返回看板后恢复分段、筛选、滚动位置和选中行。

“解释这次变化”应基于已有可验证事实。没有可靠事件或新闻来源时，只能说明观察到的价格变化，不能编造导致涨跌的原因。

## 9. 让其他用户真正用起来：引导、错误与信任

### 9.1 重写首页和安装入口，不先重命名整个仓库

建议 README 第一屏只回答：这是做什么的、当前推荐哪个客户端、是否已公开发布、哪些能力需要云端、数据存在哪里。之后分别进入“小程序使用”“桌面使用”“开发与部署”。

历史说明保留，但移入明确归档的章节或文件，并注明最后适用版本。版本矩阵至少列客户端、数据格式、支持市场/币种、AI 模式、部署前提和已知限制。不要把早期测试假数据说明放在当前生产使用步骤旁边。[S01][S02][S03]

桌面首次引导目前包括配置 AI、录入交易及示例体验等入口。建议改成实际任务式清单：确认本地存储可用、创建第一条记录、核对第一项持仓、了解备份；完成依据是操作结果，而不是用户关掉了弹窗。[S09]

### 9.2 错误提示必须告诉用户下一步

建议统一“发生什么 → 影响什么 → 现在可做什么”，并让本地记录始终有可用退路。

| 场景 | 不建议 | 建议 |
|---|---|---|
| 行情暂不可用 | 请求失败 | 当前报价不可用，已保留上次数据及时间；可重试或继续记录 |
| AI 未获授权 | AI 不可用 | 本地持仓和手记可继续使用；本轮未发送，查看授权状态 |
| 分析结果未知 | 分析失败，请重试 | 请求可能已执行，先查询原请求状态，避免重复提交 |
| 保存未确认 | 保存失败 | 尚未确认落盘；显示待核验状态及安全恢复入口 |
| 持仓校准冲突 | 数据异常 | 这份截图之后发生过交易；查看差异后决定如何校准 |
| 用户没有记录 | 空白页 | 给出一个与当前页面有关的首个动作 |

诊断页可以分成存储、数据源、云端授权、模型、版本五项。导出诊断包默认只含错误码、版本、请求状态和去敏后的运行信息，不包含持仓金额、原图、密钥和完整对话。

### 9.3 明确删除、备份和恢复的边界

桌面原文删除后的历史快照保留，与小程序删除派生分析的行为并不相同；应按实际实现清楚解释，不使用一句“删除成功”掩盖差异。[S16][S32]

产品应提供可理解的预览：将删除哪些原文、哪些依赖分析、哪些用户想法和回访；哪些导出的离线备份仍由用户自行保管。已发送给外部模型的数据不能声称可以从所有外部系统即时撤回。

原文删除或排除后，新的检索不得再次带出它。完整备份恢复后，旧待处理请求不得自动重发；当前工作区已有相关隔离设计，应加回归验证而不是替换它。[S32]

### 9.4 本地优先不等于不需要安全边界

以下是**建议验证的威胁模型**，不是本次发现的可利用漏洞：

| 边界 | 必须验证 |
|---|---|
| 用户与用户 | 身份由服务端可信上下文确定，不能信任请求自报的拥有者 ID |
| 本地与云端 | 明确传输了哪些内容，默认不传无关完整账户 |
| 模型与应用 | 模型输出是非可信数据，不可触发任意工具、删除或写账 |
| 行情与个人原文 | 外部文本和个人备注不能通过提示注入获得更高权限 |
| 供应商与服务 | 服务端密钥不下发；错误、日志、备份和诊断不泄密 |
| 导入与账本 | 图片、文本及 CSV 都先验证，不直接执行、覆盖或入账 |
| 旧客户端与新数据 | 不支持的新结构应被明确拒绝或只读，不能静默损坏 |
| 公开部署与本地 API | 保持本地监听边界；不能把本地接口原样开放到公网 |

行情和模型服务的公开使用、展示归属与再分发权限，需要按实际供应商和部署用途核验。本报告不提供未经核实的授权或法律结论。

## 10. 技术改造：统一契约，不进行大规模重写

### 10.1 先收敛边界

建议分四层：

```text
领域事实层：账本、校准、成本、估值、日期口径
应用服务层：研究准备、日历投影、决定、回访
适配层：本地存储、Python API、云函数、行情和模型供应商
呈现层：小程序 / Web / 桌面壳
```

已有 TypeScript 共享包继续服务相关客户端；Python 端通过版本化 JSON 契约和共同黄金算例对齐。不要要求 Python 直接导入 TypeScript，也不要为了代码“看上去统一”强行将本地服务迁往云端。[S41][S42][S44]

最应该共享的是资产身份、金额字符串、币种、价格基准、状态、时间和测试用例。页面组件不必强行共享。

### 10.2 拟议的估值结果契约

下面是**设计建议，不是当前 API 的真实返回结构**：

```typescript
type ValuationDisplay = {
  instrumentId: string;
  currency: string;
  value: string | null;           // Decimal 字符串
  cost: string | null;
  unrealizedPnl: string | null;
  quality: "current" | "delayed" | "stale" | "historical" | "unknown";
  basis: "market_quote" | "official_nav" | "historical_snapshot" | "missing";
  asOf: string | null;
  availableAt: string | null;
  sourceId: string | null;
  ledgerRevision: string;
  coverageEligible: boolean;       // 能否计入当前估值覆盖率
  reasonCodes: string[];
};
```

补充原则：

- 展示结果和真实估值分别命名；不能把历史截图混入 `current`。
- “延迟程度”“是否过期”“价格基准”不是同一维度；上述简化字段在落地前应映射现有契约，避免丢掉已有信息。
- 统一纯函数负责判定和计算；组件只做格式化，不能各自补一个成本价。
- 聚合返回覆盖数、缺失数和金额范围，不能只返回一个容易误读的数字。

### 10.3 拟议的关联扩展

优先检查现有 `JournalEntry`、会话、消息、分析和来源结构，在它们上面做最小扩展。以下名称仅用于说明：

| 信息 | 最小新增内容 | 存储原则 |
|---|---|---|
| 个人想法关联 | 来源消息 / 分析 / 会话、标的引用 | 原文仍是用户正文，AI 文本不自动改类 |
| 用户决定 | 决定类型、理由、引用、计划修订 | 与真实成交分离 |
| 回访事项 | 日期或结构化条件、状态、来源决定 | 只有用户确认后激活 |
| 回访结果 | 检查时间、所用事实、结果或缺失原因 | 结果缺失也是合法状态 |
| 交易关联 | 指向已有 ledger event 的引用 | 不复制、不新增虚构成交 |

存在 `user_decision` 等类型，并不等于完整决策产品链路已经实现；先复用和补齐引用验证，不能看到同名类型就认为无需改动，也不能另起一套重名数据。[S25][S32]

### 10.4 迁移和回滚

每项持久化结构变更都应有旧样本、迁移预览、备份、引用校验、读回核验和失败回退。具体 schema 版本由实施时的当前版本加一，不能仅凭历史文档固定写死一个版本号。

旧笔记没有来源关联时，用空引用标识“历史未关联”，不要用 AI 猜测原消息。新版本保存后，旧客户端是否可读必须有明确策略；无法降级时提示恢复备份，而不是静默丢掉字段。

### 10.5 导航和查询

桌面给工作区增加可恢复 URL 状态，最少包括视图、日期、标的和会话。路径格式由现有路由设计决定，不必一次拆成大量页面。

小程序保留适配其平台的导航方式，携带工作区和稳定资产引用；返回时恢复原页面状态。不要将账户金额、密钥或完整问题正文放入 URL。

### 10.6 工程拆分时机

当前核心文件承担多种职责。建议先加特征测试，再按“估值展示、日历查询、关联记录、导入校准”等边界拆出纯函数和服务。不要先为了文件行数进行机械拆分。

建议建设共享黄金夹具：同一组金额、成交、校准、行情缺失和日期边界输入，由小程序/共享域及 Python 适配分别验证。跨语言一致性应建立在契约与期望值上，而不是对某个旧实现逐字复刻。

## 11. 测试、评估与发布门槛

### 11.1 必须覆盖的回归场景

下表是**待实现或待核查的测试清单**，不是本次项目实测结果。

| 组别 | 关键用例 | 必须得到的结果 |
|---|---|---|
| 估值计算 | 涨 10%、跌 10%、平盘、缺昨收 | 合成基准正确；缺失不变成 0 |
| 截图适用性 | 数量变化、卖后买回、成本改变、校准冲突 | 失效截图只作为历史来源，不进入当前合计 |
| 汇总 | 一项缺价、多项过期、仅自选有报价、空仓 | 覆盖率及 0 / 未知语义一致 |
| 多币种 | CNY、USD 并存，无可靠汇率 | 不直接跨币种相加 |
| 日期 | 上海午夜、纽约跨日、夏令时、事后补记 | 交易日、归档日、写入时间不混用 |
| 真实历史 | 截图更新、局部导入、识别失败、重复导入 | 不制造成交、不误删未显示的持仓 |
| 日历 | 月初不同星期、闰日、空日、不同类型 | 布局正确、可新增、可打开 |
| 缓存 | 新增/修订/删除手记、跨月移动、分析完成 | 日期与计数即时更新，无幽灵条目 |
| AI 引用 | 原文版本变化、排除、删除、来源缺失 | 只引用本轮允许且可追溯的来源 |
| 决策关联 | 保存想法、修改决定、关联真实成交 | 来源不丢失，交易不重复 |
| AI 执行 | 双击、断网、超时未知、恢复旧备份 | 同一请求不重复执行或错误自动重发 |
| 存储 | 写入中断、容量不足、损坏分区、迁移失败 | 可诊断、可恢复，不以空数据覆盖真数据 |
| 云成本 | 并发、额度边界、结果未知、供应商报错 | 预算原子扣占，不绕过上限 |
| 隔离 | 两个测试身份交叉访问与伪造引用 | 无越权读取、修改或查询状态 |
| UI | 小屏、大字号、键盘、读屏、深色模式 | 不截断关键金额与状态，不依赖颜色传义 |
| 无 AI | 未配置、未授权、模型不可用 | 本地记录和查看仍完整可用 |

日期用例中还应包括基金净值晚发布、不同市场休市和数据源交易日不明。没有可信交易日历时，以明确的未知状态退化，不能只用“周一至周五”推断全部交易状态。

### 11.2 AI 评测集：先少量、可复查

建议建立一组经去敏处理或人工合成的固定场景，先覆盖：持仓变化、计划未确认、部分行情缺失、互相矛盾的原文、已删除记录、历史截止时间、相似 ticker、AI 历史自我引用。

每个场景定义四件事：允许使用的来源、禁止得出的结论、关键应提到的限制、应向用户索取的缺失信息。模型输出不用逐字匹配，但来源约束和数值必须机器校验。

**发布阻断断言：** 引用越界、将未知金额说成确定值、泄露其他用户数据、伪造实际成交、绕过明确预算，必须在强制用例中全部阻断。这里的“全部”是对测试集的门槛，不是对开放世界零风险的承诺。

### 11.3 产品指标

先做基线测量，再设改进目标；以下不是已经获得的数据。

| 指标 | 定义建议 | 防止错误激励 |
|---|---|---|
| 首次有效记录完成率 | 完成并核对第一项持仓或交易的用户占比 | 不把导入示例数据算真实激活 |
| 账户状态理解率 | 用户能否正确指出金额是否完整、数据来自何时 | 不只问界面是否好看 |
| 历史记录找回率 | 能否找到某次判断及原始依据 | 不以点击次数冒充成功 |
| 有效复盘完成率 | 回访后保存结论或明确缺数据的比例 | 不强迫每次执行交易 |
| 上下文相关性 | 用户判断所带资料是否相关且无多余泄露 | 不以提示词长度为质量 |
| AI 来源可追溯性 | 重要事实是否可对应到本轮来源 | 不由模型自评代替验证 |
| 单次有效研究成本 | 成功保存且被使用的研究消耗 | 不能靠缩短或遗漏必要上下文优化 |
| 数据恢复成功率 | 按可重现实验完成恢复的比例 | 不把未验证的保存当作成功 |

优先使用本地、聚合或用户同意的统计。不要为了埋点上传用户持仓、个人判断原文和交易明细。

### 11.4 CI 与发布验收应分层

根脚本已提供不同检查入口，而所读 CI 没有显式串起全部生产和云端专项检查；应先梳理实际依赖，再补 required checks，不能把“构建会顺带编译 Gateway”等同于“Gateway 测试已执行”。[S04][S08][S43]

建议分成：快速纯函数与契约、跨端黄金用例、客户端构建、生产假数据排除、云包及凭据检查、交互端到端、微信真机和云端实际隔离验证。

生产凭据缺失的项记为 **NOT RUN / BLOCKED**，不能改成 mock 后标为真实发布通过。发布清单记录 SHA、dirty 状态、客户端版本、构建配置、云包摘要和迁移版本，复用已有清单能力。[S35]

## 12. 实施顺序、取舍与边界

详细任务见配套 [CODEX_IMPLEMENTATION_PLAN.md](CODEX_IMPLEMENTATION_PLAN.md)。建议每轮只执行两个 Phase，并在继续前检查测试和数据变更。

| 批次 | Phase | 主要交付 |
|---|---|---|
| 第一轮 | 00–01 | 固定基线、建立复现测试、修复小程序估值与截图适用性 |
| 第二轮 | 02–03 | 修复桌面账本/指标语义，补范围确认与生产成本门槛 |
| 第三轮 | 04–05 | 修复日历查询和导航，连接想法、决定及回访 |
| 第四轮 | 06–07 | 完善总览、新用户引导及稳定可比较的看板 |
| 第五轮 | 08–09 | AI 质量评测、恢复与性能验证、文档和发布验收 |

这是依赖顺序，不是工期承诺。只发布小程序时，桌面特有修复不应被伪装成小程序已有缺陷；桌面仍受其自身 P0 发布门槛约束。两端可分别交付，但共同契约变更需要兼容检查。

### 12.1 本阶段不建议做

不进行全端重写，不新建第三套客户端，不急着引入向量数据库或多 Agent 平台，不以自动交易作为增长点，不用未经验证的收益曲线美化主页，也不把所有数据默认同步上云。

多账户、穿透式 ETF 敞口、完整现金流收益、跨币种总资产、外部事件自动跟踪都可能有价值，但应在身份、数值、时间和来源基础稳定后再排入后续路线。

### 12.2 最小但有辨识度的完成状态

用户可以在没有 AI 的情况下建立记录；打开总览知道自己持有什么、哪些数字不完整；从某项持仓发起带来源的研究；写下自己的决定；下一次回来时能找到当时依据和后续变化。

**这比增加十个市场指标，更接近“长期理解我的投资助手”。**

## 附录 A：独立算式复核说明

本次仅对三个合成算例使用 Decimal 独立校验，不导入项目代码、不连接行情或模型，也不代表通过了仓库测试。实际集成仍应在 Phase 01 中复现。

```python
from decimal import Decimal

q = Decimal("10")
previous_close = Decimal("100")

for price_text in ("110", "90", "100"):
    price = Decimal(price_text)
    rate = (price - previous_close) / previous_close
    expected = q * (price - previous_close)
    corrected = q * price * rate / (Decimal("1") + rate)
    assert corrected == expected
```

此段只验证固定数量、同一基准下的代数关系。它没有处理日内交易、费用、分红、公司行动、缺失数据或供应商基准差异，因此不是完整生产算法。
